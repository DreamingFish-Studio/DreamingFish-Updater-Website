创建第一个项目

上一页完成了首次设置，让我们继续配置吧！下面我们先走一遍 Web 配置模式——这是推荐的方式；习惯用终端的朋友，也可以直接跳到文末的交互式命令行版本。

Web 配置模式#

这是推荐的方式。按 Y 后管理端会自动启动 Web 管理界面。下面就是按 Y 后终端显示的内容：

按 Y 后 · Web 管理界面启动
Web 管理界面已启动，监听：127.0.0.1:18080

如果管理端运行在当前电脑：
  请直接在浏览器打开：http://127.0.0.1:18080/

如果管理端运行在远程服务器且保持安全的 127.0.0.1 监听：
  1. 在您自己的电脑上打开终端，运行以下 SSH 隧道命令：
     ssh -N -L 18080:127.0.0.1:18080 用户名@您的服务器地址
  2. 保持 SSH 窗口运行，再在自己电脑的浏览器打开：
     http://127.0.0.1:18080/
同机 Caddy/Nginx 可代理 127.0.0.1 到公网 443，这是推荐部署方式。

按 Ctrl+C 停止服务并返回主菜单。
i
怎么打开 Web 管理页面？

管理端就在当前电脑：直接在浏览器打开 http://127.0.0.1:18080/。管理端在远程服务器：先在自己电脑上运行 ssh -N -L 18080:127.0.0.1:18080 用户名@您的服务器地址，保持这个终端窗口运行，再打开 http://127.0.0.1:18080/。不要把 18080 直接暴露到公网——就算不小心暴露了，没有注册的管理账户和会话令牌也连不上管理功能，远程登录还强制要求 HTTPS；但依然不建议暴露，正确做法是 SSH 隧道加 HTTPS 反向代理。

第 2 步 · 创建项目#

登录后，点击概览页的“＋ 新建项目”，让我们来创建第一个项目吧！弹出的表单里只有四个必填项：项目 ID、项目显示名称（会以标题字样显示在玩家端的更新器里）、要管理的文件目录和玩家端更新器访问地址，其余可以先留空。「强制同步一级目录」先不要填写，两种管理模式的区别，下面马上就会讲。

这里有三个容易出错的地方，先提醒你：

  • 项目 ID：创建后不要随意改。
  • 要管理的文件目录：这是你要管理的文件目录，不要和管理端 data 混在一起。
  • 玩家端更新器访问地址：必须是玩家电脑能访问的公网地址（例如公网端口映射到内部 8080），不能填 127.0.0.1 或内网地址。

创建项目后，这个项目的信息你还可以在「项目设置」里继续修改，比如给玩家端更新器填写副标题（额外设置，不填也可以）。

两种同步模式#

这就是第 2 步里我们让你先不要填写「强制同步一级目录」的原因——管理端有两种同步模式：

默认同步

只维护明确托管的内容

发布清单中的文件缺失或损坏时恢复；不在清单中的玩家额外文件默认保留。玩家可以对普通托管内容设置本地豁免。

  • 适合大多数整合包项目
  • 保留玩家兼容配置与自选模组
  • 文件管理边界清晰、温和
强制同步

强制和远程服务器同步

指定范围内的内容以服务器为准：文件会被强制覆盖，玩家会无法自己添加模组，多出来的文件会被移入归档。

  • 适合核心模组和关键配置
  • 可以按一级目录整体强制，或只强制单个文件
  • 设置变化需要重新扫描并发布

强制同步分为强制同步目录和强制同步文件两种：前者按一级目录整体递归强制，比如把 mods 设为强制目录；后者只指定单个文件，比如 config/server-required.toml。

i
强制同步单个文件和默认同步有什么区别？

你可能会问这个问题：强制同步单个文件的作用，就是可以防止玩家豁免某个文件。比如核心模组，或者你的服务器可能有一些反作弊模组，你可以用强制同步来防止玩家禁用它。

不过，大部分情况下其实都不需要设置强制同步：默认同步已经适合绝大多数整合包项目，等真正遇到需要锁定的内容（比如核心模组、反作弊）时，再按需开启也不迟。

第 4 步 · 扫描并发布#

接着向下滑，点击“↻ 扫描整合包目录”，先看变更预览：新增、修改、移除的文件和预计下载量。重点检查移除后的处理：从玩家端删除，或放弃管理并保留玩家副本。不过，第一次发布应该都是「新增」，基本不会遇到移除；如果以后需要删除，管理端会逐个询问处理方式。

确认无误后填写本次显示版本（如 1.0.0）、最低玩家端程序版本和更新记录，点击“发布整合包”。发布是不可变的：内容有误就修正目录再发新版本，不要修改旧版本。

第 5 步 · 制作玩家端（发布玩家端程序）#

刚刚我们已经发布了整合包文件。接下来，你需要第一次发布玩家端程序：把整合包数据、玩家端个性化设置、公网地址，以及最重要的网络传输公钥，一起打包进玩家端（私钥会留在管理端，由服主自己保管）。

玩家端程序和整合包版本是两条独立的发布线：以后只更新模组或配置时，重新发布整合包就好，不用再动玩家端程序；反过来，要发布玩家端程序时，也不用动整合包。

打开“玩家端程序”页，跟着这几步走就行：

  1. 选好平台，和玩家实际用的一致就好，比如 windows-x64。
  2. 填一下最低 Bootstrap Agent 版本，目前是 0.1.2——Agent 一般不会更新，只有重新发了更高版本时才需要提高。
  3. 选玩家端发行包解压后的根目录，管理端会自动在里面定位版本目录和 DreamingFishUpdater.exe；别选 ZIP 本身。
  4. 点“发布玩家端”，剩下的交给管理端：自动读版本、定位 app-image、生成清单并签名。

让启动器加载 Bootstrap Agent

!
先确认版本隔离真正生效

实际游戏目录必须是当前版本目录，例如 .minecraft/versions/Dreamingfish-Building。HMCL 的“当前版本独立设置”可能覆盖全局版本隔离；不要只看开关，测试启动后还要确认最终命令中的 --gameDir 指向当前版本目录。

使用 PCL 时，优先在该版本的 JVM 参数中填写下面这行：

PCL 推荐参数
-javaagent:"{verpath}.dreamingfish-bootstrap/bootstrap-agent.jar"

{verpath} 是 PCL 提供的版本目录占位符，启动时会自动变成当前版本的真实路径。它不能用于 HMCL 或其他启动器，也不要改成服主电脑上的绝对路径。

版本 JSON 的 arguments.jvm 是 PCL、HMCL 两者通用的接入方式。如果希望同一个整合包同时兼容 PCL 和 HMCL，可以使用下面的方法；不要把 ${game_directory} 直接填进 HMCL 的“Java 虚拟机参数”输入框。

打开 .minecraft/versions/版本名称/版本名称.json，找到 "arguments" 里面的 "jvm" 数组，并在数组开头追加下面这一项：

PCL、HMCL 通用 · arguments.jvm 新增项
"-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar"

例如，原文件是：

修改前（示例）
"arguments": {
  "jvm": [
    "-Djava.library.path=${natives_directory}"
  ]
}

添加后应变成：

修改后（示例）
"arguments": {
  "jvm": [
    "-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar",
    "-Djava.library.path=${natives_directory}"
  ]
}

示例中的原参数只是演示位置；你自己的 jvm 数组可能有更多内容，必须全部保留，只新增一行并注意英文逗号。保存后完全退出并重新打开启动器，让它重新读取版本 JSON；不要设置 Windows 全局 JAVA_TOOL_OPTIONS。

PCL 用户优先使用前面的 {verpath} 参数即可；需要兼容 PCL 和 HMCL 时使用版本 JSON。同一个实例不要同时配置两种方式，否则 Agent 会被加载两次。

i
分发前必须检查最终启动命令

正确结果应包含已经展开的绝对 Agent 路径，而不是字面量 ${game_directory} 或 {verpath}。如果启动器执行了“修复版本”、重新安装 Forge 或重建版本 JSON，请再次确认该条目没有被覆盖。

分发时，你可以直接把整个版本目录发给玩家，也可以用启动器导出整合包再分享。导出整合包时要注意：整合包文件夹里要包含玩家端文件——就是刚拖进去的 .dreamingfish-bootstrap（隐藏文件夹，别漏）和 DreamingFishUpdater，缺了它们，玩家拿到手也不会有更新器。

第 6 步 · 启动下载服务#

回到“概览”，点击“▶ 启动下载服务”，服务状态变为运行中。玩家更新器就是从这个服务下载清单和文件。

在主菜单选择 [2] 创建项目。和 Web 表单一样，真正必填的是四项：项目 ID、项目显示名称、整合包文件目录和玩家访问公共 HTTP 地址；副标题、服务器地址、颜色和封面都可以直接按回车使用默认值。

两种同步模式#

这就是创建项目时建议先留空强制同步设置的原因：终端和 Web 使用完全相同的同步规则。

默认同步

只维护明确托管的内容

发布清单中的文件缺失或损坏时恢复；不在清单中的玩家额外文件默认保留。玩家可以对普通托管内容设置本地豁免。

  • 适合大多数整合包项目
  • 保留玩家兼容配置与自选模组
  • 文件管理边界清晰、温和
强制同步

强制和远程服务器同步

指定范围内的内容以服务器为准：文件会被强制覆盖，玩家会无法自己添加模组，多出来的文件会被移入归档。

  • 适合核心模组和关键配置
  • 可以按一级目录整体强制，或只强制单个文件
  • 设置变化需要重新扫描并发布

强制同步一级目录会递归管理整个目录，例如 mods。目录中的文件不能被玩家豁免，玩家额外放入的文件也会被归档移出；以后新增到该目录的文件会自动属于这个规则。

强制同步文件只锁定指定文件，例如 config/server-required.toml。它的主要作用是禁止玩家豁免该文件，不会清理同目录的其他文件，以后新增文件也不会自动加入。

i
大多数项目不需要强制同步

默认同步已经适合绝大多数整合包。只有核心模组、反作弊或必须保持一致的配置，才建议按需启用强制同步；规则修改后仍需重新扫描并发布才会生效。

第 4 步 · 扫描并发布#

重点检查移除后的处理。普通托管文件可以选择“从玩家端删除”，或者“只放弃管理并保留玩家本地文件”；强制同步目录中的文件只能随发布从玩家端移除。第一次发布通常全部是“新增”，基本不会出现这一步。

第 5 步 · 制作玩家端（发布玩家端程序）#

整合包文件发布完成后，第一次还需要发布玩家端程序。这个过程会把整合包数据、玩家端个性化设置、公网地址和网络传输公钥一起准备好；签名私钥始终留在管理端数据目录，不会进入玩家部署包。

玩家端程序和整合包版本是两条独立的发布线：以后只更新模组或配置时，重新发布整合包即可，不需要再次发布玩家端程序；只有更新器程序本身升级时，才需要重新执行 [6]。

在主菜单选择 [6] 发布玩家端程序，依次完成下面四项：

  1. 选择和玩家电脑一致的平台，Windows 通常保持 windows-x64。
  2. 填写玩家端发行包解压后的根目录。管理端会自动定位版本目录和 DreamingFishUpdater.exe，不要填写 ZIP 文件、app、runtime 或具体版本子目录。
  3. 填写最低启动引导器版本，当前通常保持 0.1.2；只有重新分发了更高版本 Bootstrap Agent 时才提高。
  4. 核对后输入 Y，管理端会自动读取程序版本、定位 app-image、生成清单并签名。

接下来，让启动器加载 Bootstrap Agent。使用 PCL 时，优先在该版本设置的「JVM 参数」（Java 虚拟机参数）中填写：

PCL 推荐参数
-javaagent:"{verpath}.dreamingfish-bootstrap/bootstrap-agent.jar"

{verpath} 是 PCL 专属占位符，启动时会自动替换成当前版本目录。HMCL 和其他启动器不能使用它。

版本 JSON 的 arguments.jvm 是 PCL、HMCL 两者通用的接入方式。需要让同一个整合包兼容两种启动器时，打开 .minecraft/versions/版本名称/版本名称.json，找到 "arguments" 中已有的 "jvm" 数组，在数组开头追加：

PCL、HMCL 通用 · arguments.jvm 新增项
"-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar"

例如原来是：

修改前（示例）
"arguments": {
  "jvm": [
    "-Djava.library.path=${natives_directory}"
  ]
}

添加后是：

修改后（示例）
"arguments": {
  "jvm": [
    "-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar",
    "-Djava.library.path=${natives_directory}"
  ]
}

你自己的原有 JVM 参数必须全部保留，只新增一行并注意英文逗号。保存后完全退出并重新打开启动器；不要把 ${game_directory} 直接填进 HMCL 的 JVM 参数框。PCL 用户优先使用前面的 {verpath}；同一个实例不要再同时配置两种方式。

!
分发前检查一次实际启动命令

确认 --gameDir 指向当前版本隔离目录，并且 -javaagent 后面已经是实际路径，而不是未替换的 {verpath} 或 ${game_directory}。

分发时，你可以直接把整个版本目录发给玩家，也可以用启动器导出整合包再分享。导出整合包时要注意：整合包文件夹里要包含玩家端文件——就是刚拖进去的 .dreamingfish-bootstrap（隐藏文件夹，别漏）和 DreamingFishUpdater，缺了它们，玩家拿到手也不会有更新器。

最后在主菜单选择 [9] 启动 HTTP 文件服务。这与 Web 概览页的“启动下载服务”是同一项服务：玩家更新器会通过项目的公网地址从这里下载清单和文件。服务运行期间按 Ctrl+C 停止并返回主菜单：

启动 HTTP 文件服务 · [9]
启动只读 HTTP 文件服务 http://0.0.0.0:8080/？ [Y/n]：y
HTTP 文件服务已启动：http://0.0.0.0:8080/
健康检查：http://0.0.0.0:8080/healthz
按 Ctrl+C 停止服务并返回主菜单。

验证方式也和 Web 模式相同：先在管理服务器上访问 http://127.0.0.1:8080/healthz，应返回 {"status":"ok"}；再从另一台电脑访问项目中填写的公网地址，确认公网端口已经正确映射到下载服务端口。服务运行期间管理端进程必须保持运行，Linux 可以放在 tmux 会话中，断开 SSH 后服务仍会继续。

如果管理了多个项目，操作前会先列出项目让你选择，直接回车使用带 * 的默认项目：

多项目选择
请选择项目：
[1] 梦屿 (dreamhaven) *
[2] 建筑服 (build-server)
输入编号或项目 ID，回车使用 * 项目：

到这里，命令行模式已经完成了与 Web 模式相同的六个步骤：创建项目、准备文件、设置同步策略、扫描发布、制作玩家端和启动下载服务。两种操作方式共用同一套项目与发布数据，可以随时切换。日常维护——修改项目设置 [3]、查看发布历史 [5]、发布玩家端程序 [6]、制作玩家实例 [7]、修改服务设置 [8]——都在主菜单里；备份与恢复等终端专属功能，见「日常维护」。

玩家启动前

只处理本机差异

  1. 01

    比较本地文件

    玩家仍然从 PCL、HMCL 等启动器进入游戏，更新器在启动前自动比较本机文件与目标版本。

  2. 02

    下载变化内容

    只下载真正发生变化的文件，不必每次重新下载整个整合包；多个文件同时下载，大文件中断后也能接着传。

  3. 03

    暂存并校验

    新文件先写入临时位置，逐一检查大小与 SHA-256，确认完整后才会进入安装。

  4. 04

    异常时恢复

    替换前先完成备份；中途退出或安装失败时恢复到更新前的状态，不会留下更新到一半的客户端。

  5. 05

    继续启动游戏

    一切完成后，Minecraft 继续启动，玩家不需要再手动处理任何文件。

Integrity and atomicity

先确认发布来自谁，再确认每一个字节是否正确，最后才写入实例。

DreamingFish Updater 不把“下载成功”当作“更新可信”。发布身份、对象内容、安装结果和本地路径分别校验；任何一步不满足条件，更新都不会被标记为完成。

管理端私钥只保存在服主自己的管理数据中。玩家端只持有公钥，因此公共下载服务或网络链路无法自行伪造一个可信发布。

02 / VERIFIED TRANSFER传输完整性
OBJECTsha256/8f4c…d91a
声明大小与响应范围检查SHA-256 VERIFIED
  • 每个文件对象以 SHA-256 内容哈希标识，同时校验声明大小。
  • 断点续传必须返回匹配的 Content-Range，不匹配就重新下载。
  • 下载先写入分片文件，校验通过后才提升为可安装对象。
  • 默认并行下载多个独立对象，但每个对象都单独完成完整性验证。
Atomic installation

安装不是边下边覆盖，而是一份可以恢复的事务。

真正改动实例前，系统先备份本轮涉及的文件与可信元数据，并写入事务日志。替换完成后重新校验目标状态；只有校验、元数据保存和归档都完成，事务才会进入已提交状态。

1BACKED_UP备份旧文件与发布元数据
2COMMITTING临时文件落盘并替换目标
3VERIFYING重新验证已安装文件
4COMMITTED保存可信状态并清理事务
transaction.log
    意外断电、进程退出或安装失败下次启动先读取事务日志；未完成提交时恢复备份，恢复失败则明确阻止继续启动，而不是假装更新成功。

    原子文件替换

    内容先写入同目录临时文件、强制刷新到磁盘，再使用原子移动替换；文件系统不支持时退回安全替换路径。

    路径安全

    拒绝绝对路径、..、Windows 保留名、大小写冲突和符号链接穿越，发布文件不能逃离实例目录。

    并发与运行锁

    同一实例只允许一个更新任务；Minecraft 正在使用实例时，不执行提交或未完成事务恢复。

    离线边界

    网络不可用时只复用最近一次已验证安装。签名、哈希、路径或事务错误不会被伪装成普通断网。

    关于 HTTP 与 HTTPS

    公共文件源可以部署在 HTTP 或 HTTPS 上。内容真实性与完整性由 Ed25519 签名和 SHA-256 校验独立保证：被篡改、截断或替换的清单与文件不会进入安装流程。正式公网环境仍建议使用 HTTPS，以额外保护访问地址、请求元数据和网络隐私。
